# 独立长连接服务器架构改造计划

## 1. 目标与已确认约束

本计划把项目建设为独立的长连接服务器，提供 WebTransport（WT）和 WebSocket（WS）两种接入方式。客户端优先使用 WT；WT 无法建立连接时，由客户端重新连接 WS。两个传输层共享连接管理、消息模型和业务 Handler。

已确认的架构约束：

- WT 指 WebTransport，计划使用 Rust `wtransport` crate 实现；WS 保留现有 Actix Web 接入。
- 传输层只负责协议连接、帧/流收发、生命周期和错误转换；不直接实现聊天业务。
- JSON 是首期线上消息格式；预留 codec 接口，protobuf 暂时不实现，只保留扩展位置/空实现边界。
- PostgreSQL 用于联系人与用户关系数据。
- MongoDB 用于消息记录的持久化与增量查询。
- 健康模块每 10 分钟向注册中心报告一次节点健康状态。
- WT 建连失败后的 WS 降级由客户端发起。服务端不能把一个未成功建立的 WT 会话转换成 WS 会话。

## 2. 目标架构

```text
                         ┌─ WebSocket Adapter（Actix Web） ─┐
客户端：WT 优先，失败后 WS ┤                                  ├─ 统一连接/消息接口
                         └─ WebTransport Adapter（wtransport）┘
                                                               │
                                JSON Codec ─ 内部消息模型 ─ 共享 Handler
                                Protobuf Codec（后续实现）       │
                                               ┌───────────────┼──────────────┐
                                               │               │              │
                                      Connection Registry  PostgreSQL     MongoDB
                                      房间/发送队列/会话      联系人与关系    消息记录
                                                               │
                                                Health Reporter ─ 注册中心
                                                （每 10 分钟报告）
```

建议在现有 `server` 二进制中先以独立模块实现两个 listener。WT 需要 HTTP/3、QUIC、TLS 和 UDP 端口，不能假设它可以作为 Actix Web 的普通 WS 路由挂载。如果 `wtransport` 与现有 Tokio/运行时或 TLS 配置无法可靠共存，再评估拆成同一仓库下的独立进程；共享业务协议仍通过 crate/API 边界复用。

## 3. 分层职责

### 3.1 Transport Adapter

WS 与 WT 各自实现 Adapter，并统一提供以下生命周期能力：

- 接受连接，生成/获取 `ConnectionId`，提供传输类型与会话元信息。
- 收取协议数据并交由 Codec 解码。
- 从连接发送队列获取服务端消息，编码并写入对应协议。
- 转换 ping/pong、关闭、超时、异常等协议事件为统一连接事件。
- 断开时注销连接，并触发会话清理。

WS Adapter 继续使用 Actix Web；WT Adapter 使用 `wtransport`。两者不得把 `WebsocketContext`、Actix Actor 地址、WebTransport Session/Stream 类型泄漏到共享 Handler 或房间服务。

### 3.2 Codec 与内部消息模型

- 定义传输无关的客户端消息、服务端消息、协议错误及 codec 接口。
- 首期 JSON Codec 负责将 WS 文本帧或 WT 约定的数据载荷解码成内部消息，并完成反向编码。
- 不要求 WS 与 WT 在线上使用相同帧类型；只要求二者解码到相同的内部模型。
- 为协议版本和格式协商保留字段/边界。不得通过猜测帧内容静默切换格式。
- protobuf 首期不启用。预留独立 codec 模块/trait 实现位置；未实现时显式返回“不支持”，不伪装为可用能力。
- 解码前后均需设置消息大小上限，并对格式错误、未知版本和不支持类型给出可观测错误。

### 3.3 共享 Handler 与服务层

共享入口接收统一的 `SessionContext`、内部消息及应用服务依赖，不接收传输层专属上下文。职责包括：

1. 校验消息结构、身份/权限上下文、大小和业务约束。
2. 根据事件与消息 channel 分发到业务用例。
3. 调用房间/连接服务进行点对点发送或广播。
4. 按消息持久化策略调用 MongoDB 消息仓储接口。
5. 必要时查询 PostgreSQL 联系人/关系仓储接口。
6. 返回统一业务错误；Adapter 再将错误映射成协议层响应或关闭原因。

Handler 不直接执行 SQL/MongoDB 查询、不序列化 WS/WT 帧、不依赖 Actix Actor 类型。公共消息、单聊、群聊等业务路由可以共享同一入口；当前尚未实现的业务分支应明确返回未支持或维持 TODO，不在传输层重构中扩大业务范围。

### 3.4 连接注册表、房间和发送队列

当前房间成员保存 `actix::Addr<ChatSession>`，需改为传输无关结构：

- `ConnectionRegistry`: `ConnectionId -> ConnectionHandle/发送通道`。
- `RoomRegistry`: `RoomId -> ConnectionId 集合`。
- 每个连接使用有界 outbound queue，避免慢客户端导致内存无界增长。
- 广播先解析目标连接，再向对应连接队列投递；目标连接自行由 WS 或 WT Adapter 写出。
- 关闭时移除连接及其房间成员，清理空房间。
- 队列满时采用明确策略（建议限流并在持续拥塞时断开慢连接），不得静默无限堆积。

这使同一个房间可同时容纳 WS 与 WT 连接，业务广播不需要区分传输类型。

## 4. WT 优先与 WS 降级流程

1. 客户端先尝试 WebTransport；客户端需要支持 HTTP/3、服务端证书受信任且网络允许 QUIC/UDP。
2. 客户端对建连设置有界超时，并区分证书/配置等不可恢复错误与网络暂时错误。
3. WT 建连失败后，客户端释放该次 WT 尝试，再按 WS 地址重新连接。
4. WT 和 WS 建连成功后均完成相同的应用层身份认证、协议版本协商和 JSON 消息处理。
5. 规划客户端实例/会话重连标识与服务端幂等处理，降低客户端误判 WT 已建成而重复建立 WS 时的重复在线影响。
6. 运行期 WT 连接中断是否也立即切换 WS，作为客户端策略配置；计划首版覆盖建连失败回退，运行期切换需确保消息重放/去重语义后再启用。

首版 WT 应选定一种消息承载方式。建议聊天消息先使用可靠双向流；WebTransport datagram 留作后续低延迟、允许丢包的业务，不让可靠聊天消息依赖不可靠数据报。

## 5. 存储边界

### PostgreSQL

- 联系人、好友/关注等用户关系及其必要索引。
- 通过关系仓储接口访问；不得承担消息记录的主存储职责。
- 检查现有 schema/migrations 是否已有对应模型，补齐迁移、唯一约束和查询索引。

### MongoDB

- 消息记录的写入、按会话/房间与时间排序的增量拉取。
- 定义稳定的消息文档 ID、会话/房间 ID、发送者、服务端时间、消息类型及 payload 字段。
- 为消息幂等写入、时间游标分页、TTL/归档策略预留明确设计；具体保留周期需产品确认。
- 由 MongoDB Repository 实现应用层消息仓储接口。

当前 `crates/storage_pg` 中有 PostgreSQL 消息仓储实现，而项目依赖中尚未发现 MongoDB driver（2026-10-26 状态：MongoDB driver 与 `MongoMessageStore` 已接入，见下方「落库模式」）。实施时应将消息仓储职责迁到 MongoDB；PostgreSQL 仓储聚焦联系人与关系。存储迁移不得隐式改变 API/消息语义。

Redis 当前已配置并被运行状态初始化，可作为缓存/在线状态的候选组件；其具体职责需确认，不替代 PostgreSQL 关系数据或 MongoDB 消息记录。

#### 落库模式：事务能力探测与顺序幂等降级（已落地，2026-10-26）

消息落库必须同时覆盖副本集/分片集群与 standalone 单机 mongod，因此写入模式按部署能力选择，而不是写死单一实现：

- 能力差异：多文档事务只在副本集（`admin.hello` 返回 `setName`）或 mongos（`hello.msg = "isdbgrid"`）可用；standalone 执行 `startTransaction`/`commitTransaction` 会报 `code 20`，这是部署能力缺口，不是代码缺陷。
- 策略配置：`[mongodb].transactions`，取值 `auto`（默认）/ `on` / `off`。非法值启动即失败，不做静默降级；`on` 用于强制要求事务的部署，`off` 用于运维/CI 显式关闭。
- 生效时机：`MongoMessageStore::from_client` 启动时按策略判定一次，结果固化在 `transactions_enabled`。`auto` 通过 `admin.hello` 探测，探测失败保守按“不支持”处理，不阻断启动。
- 事务路径（`transactions_enabled = true`）：主消息、发件箱、每个收件人的收件箱在单个事务内统一提交，任一失败整体回滚。
- 降级路径（`transactions_enabled = false`）：沿用同一套文档结构与幂等键，按 `messages` → `outbox` → `inbox` 顺序 upsert；中间失败不回滚，由客户端以相同 `message_id` 重发完成自愈。
- 幂等键：`messages.message_id`、`outbox._id = "{senderId}:{messageId}"`、`inbox._id = "{recipientId}:{messageId}"` 均为唯一索引；同一 `message_id` 携带不同 sender/device/会话/收件人/payload 时由 `ensure_same_message` 拒绝，避免重发覆盖成新内容。
- 两条路径共用文档构造函数（`outbox_payload` / `inbox_payload`）与幂等键构造函数（`outbox_id` / `inbox_id`），防止事务与降级实现字段漂移。
- 可观测性：启动日志输出 `mode` 与 `replica_set`，并明确打印“消息落库使用多文档事务”或“当前 MongoDB 不支持多文档事务（standalone），消息落库降级为顺序幂等写入”；降级写入失败时打印提示重试可幂等补齐。
- 验收：`cargo test --workspace` 全绿；`cargo test -p cola-im-chat-server --bins live_standalone -- --ignored --nocapture` 对真实 standalone 实例验证四件事——能力探测为 false、同一 `message_id` 重复投递后三类集合各仅 1 条文档、同 ID 换内容被拒、探测数据自动清理。
- 运维后续：把 standalone 改为单节点副本集（`--replSet rs0` + `rs.initiate`）并在配置中填 `replica_set` 后，`auto` 会自动回到事务路径，无需改代码。三种取值与部署形态的对应关系固化在本节，运维变更需同步更新。

## 6. 健康模块与注册中心

- 新建独立 Health/Registry 模块；服务器启动时读取节点身份、注册中心地址和上报配置。
- 首次上报/注册之后按 **10 分钟固定周期**报告健康状态，周期应配置化但默认值为 600 秒。
- 报告建议包含节点 ID、版本、状态、监听地址、WS/WT 能力、时间戳和必要的负载/连接数指标。
- 区分 liveness（进程存活）与 readiness（是否接收新连接），依赖健康（PG/MongoDB）单独表达。
- 注册中心请求使用超时和有限重试；报告失败记录日志/指标，不阻塞连接 accept、收发或共享 Handler。
- 节点退出时尽可能注销/标记下线；注册中心租约/过期策略依注册中心协议确定。
- 对健康报告任务提供可注入周期/时钟的测试方式，避免测试等待真实 10 分钟。

注册中心产品、接口格式、认证方式、租约语义目前未知；先定义 `RegistryClient` 接口，待取得注册中心契约后实现具体客户端，不猜测 Consul、Etcd 或自定义 HTTP API。

## 7. 配置与运行部署

配置至少需要覆盖：

- WS bind 地址/端口。
- WT bind 地址/UDP 端口、TLS 证书与私钥路径、HTTP/3 配置。
- PostgreSQL DSN/连接池参数（关系库）。
- MongoDB URI/数据库/连接池参数（消息库），以及多文档事务策略 `[mongodb].transactions`（`auto`/`on`/`off`，默认 `auto`）。
- 节点 ID、注册中心地址/凭据、健康周期（默认 600 秒）。
- 消息最大帧大小、连接队列容量、超时和限流参数。

凭据通过环境变量或安全配置注入，不提交真实明文密码、token、证书私钥。部署文档应列出 WT 的 UDP 可达性、证书要求及 WS 回退入口。健康任务不能因 PG/MongoDB 瞬时故障而停止运行。

## 8. 分阶段实施与验收

### 阶段 A：建立共享业务边界

- 整理内部消息类型和 `Handler`/用例接口。
- 抽象 `ConnectionId`、传输无关 outbound 消息和发送能力。
- 用单元测试覆盖现有 JSON 消息解析、公共房间路由和错误行为。

**验收：**业务 Handler 不引用 WS/Actix 类型；现有 WS 行为通过测试。

### 阶段 B：连接注册与 WS Adapter 重构

- 用 ConnectionRegistry、RoomRegistry 和有界发送队列替换 `RoomChannels` 中的 Actor 地址。
- 把现有 WS actor 降为协议 Adapter，连接/断开/消息都调用统一接口。

**验收：**WS JSON 收发和公共房间广播工作，断连能清理注册状态；没有 WS 类型从 Adapter 泄漏。

### 阶段 C：JSON Codec 与 protobuf 扩展边界

- 加入 codec trait 和 JSON 实现。
- 增加格式/版本错误测试，protobuf 保留未实现状态。

**验收：**业务层只接收内部模型；JSON 往返测试通过；protobuf 不会被误认为已支持。

### 阶段 D：MongoDB/PostgreSQL 职责落实

- 明确并迁移 PostgreSQL 联系人与关系 schema/repository。
- 增加 MongoDB driver、连接初始化和消息 repository。
- 定义并测试消息幂等写入、增量拉取和索引。
- 消息落库模式按部署能力自动选择：副本集/mongos 走多文档事务，standalone 降级为顺序幂等写入（详见 5. MongoDB「落库模式」）。

**验收：**联系人/关系只经 PG 仓储访问；消息记录只经 MongoDB 仓储访问；两套存储均有可验证的连接与集成测试；standalone 单机实例在降级模式下同样能完成幂等落库（由 `live_standalone_persist_roundtrip` 覆盖）。

### 阶段 E：WebTransport 最小垂直切片

- 锁定与当前 Rust/Tokio 兼容的 `wtransport` 版本及 TLS 方案。
- 独立启动 WT listener，完成握手、可靠双向流 JSON 收发和关闭流程。
- 让 WT Adapter 接入已验证的共享 Handler 与连接注册表。

**验收：**WS、WT 客户端发送同一 JSON 业务消息可到达同一 Handler；WT 广播可投递到 WT/WS 两类连接。

### 阶段 F：客户端回退、健康上报与整体验证

- 实现客户端 WT 优先、失败后 WS 重连约定和去重/重连标识。
- 实现 RegistryClient 与 600 秒健康报告任务、超时/重试/退出处理。
- 完成双传输并发、慢消费者、断连清理、依赖故障和部署网络测试。

**验收：**WT 不可用时客户端可通过 WS 使用相同业务能力；节点按配置周期向注册中心报告，注册中心故障不影响消息链路。

## 9. 测试策略

- 单元测试：codec、消息验证、Handler 路由、PG/Mongo repository 映射、健康状态构造。
- 传输适配测试：WS/WT 各自的建立、读写、关闭、格式错误与超时。
- 跨传输集成测试：WS 发消息到 WT 客户端、WT 发消息到 WS 客户端、跨传输房间广播。
- 存储集成测试：PostgreSQL 关系读写；MongoDB 消息幂等写入和游标拉取；standalone 降级落库路径由真实实例测试 `live_standalone_persist_roundtrip` 覆盖（`#[ignore]`，用 `-- --ignored` 显式运行，读取 `application.toml [mongodb]` 配置）。
- 健康模块测试：首次报告、周期调度、失败重试、任务退出；测试中使用短周期注入。
- 部署检查：TLS 证书、HTTP/3/QUIC UDP、防火墙、WS 回退地址和连接限额。

## 10. 实施前待确认项

以下事项作为配置/接口待定，不阻塞先行完成的传输无关抽象：

1. 注册中心的产品/API、认证、租约与注销协议。
2. WS 与 WT 是否同进程部署；WT UDP 监听地址、端口和证书由谁提供。
3. 首版 WT 仅使用可靠双向流（计划建议）还是同时开放 datagram。
4. WT 运行期断线后是否立即降级 WS，以及消息重放/幂等规则。
5. MongoDB 消息保留期、归档、分片和查询范围要求。
6. Redis 是否用于连接在线状态/缓存，或本次长连接服务器首版不依赖 Redis。
7. 联系人关系具体包含好友、关注、黑名单中的哪些模型。

## 11. 当前项目基线与风险

- 当前 WS 入口位于 `server/src/app.rs`，业务与 WS Actor 生命周期耦合在 `server/src/handlers.rs`。
- 当前 `RoomChannels` 保存 `actix::Addr<ChatSession>`，是共享双传输前优先拆除的耦合点。
- 当前入口只注册 `/ws`，未发现 WebTransport/QUIC 依赖或注册中心健康模块。
- 当前代码启动时连接 PostgreSQL；MongoDB 配置虽存在，但未发现 MongoDB driver，消息仓储代码目前在 `storage_pg` 中使用 PostgreSQL。
- 2026-10-26 更新：MongoDB 消息仓储已落地（`server/src/service/mongodb.rs` 的 `MongoMessageStore`），落库模式为「事务能力探测 + 顺序幂等降级」，见 5. MongoDB；线上实例当前为 standalone，运行时走降级路径。上述 `storage_pg` 消息仓储随迁移计划逐步退出。
- 现有工作区 `cargo check --workspace` 曾通过，但有警告；它不代表 WT、MongoDB 或注册中心已经实现或验证。
- 当前配置文件曾包含明文凭据；实施前应轮换已暴露凭据并移除仓库中的真实秘密。
