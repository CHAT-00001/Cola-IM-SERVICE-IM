# IM 未读计数与增量同步计划

## 1. 目标与范围

### 1.1 目标

- **S1｜权威未读**：服务端维护每个账号在每个会话的未读数，`/chat/session/list` 返回真实 `unread_count`，客户端不再自行猜测。
- **S2｜读清零**：新增 `POST /chat/session/read`，把一个会话的未读清零。
- **S3｜增量拉取**：新增 `GET /message/history`，用 `(conversation_id, created_at, message_id)` 游标向前翻历史，替代"每次拉 100 条"。
- **S4｜连接地址下发**：`POST /ws/ticket` 额外返回 `ws_url`，浏览器不再硬编码地址。
- **S5｜（Phase 2）未读变更推送**：新增 `Event::UnreadChanged = 15`，计数变化后向在线设备推送全量未读快照。

### 1.2 非目标

| 不做的事 | 原因 |
|---|---|
| WebTransport 服务端实现 | `Cargo.toml` 无 `wtransport`；浏览器需 HTTP/3 + TLS，本地不可用。`WtSettings`（`server/src/config.rs:265`）保持"仅配置占位"。 |
| 群聊未读（成员级计数） | `group_memberships` 无 per-member 计数列，需要独立表与写放大；先做单聊。 |
| 离线推送（APNs/FCM） | 属客户端范畴，本服务只负责在线帧。 |
| 把 `/ws` 改到其他端口 | 现有 `/ws` 与 `/ws/ticket` 同 App（`server/src/app.rs:269-273`），改动收益小、风险大。 |

### 1.3 验收标准

| 编号 | 场景 | 期望 |
|---|---|---|
| B1 | A 发消息给 B（B 不在线） | `im_2024.chat_session_members.unread_count` 中 B 的行 +1，A 的行不变 |
| B2 | B 调 `/chat/session/list` | `unread_count` 与 B1 一致 |
| B3 | B 调 `POST /chat/session/read` | 该会话 B 行归零，返回 `{session_id, unread_count: 0}` |
| B4 | 重复 `POST /chat/session/read` | 幂等，仍 200，`unread_count: 0` |
| B5 | `GET /message/history?session_id=…&limit=20` | 倒序 20 条 + `next_cursor`；带游标再请求得到更早一页，无重复无跳条 |
| B6 | `POST /ws/ticket` | 响应含 `ws_url`，与 `[chat_gateway].public_ws_url` 一致 |
| B7 | `cargo test -p server` | 全绿，含新增仓储与服务测试 |
| B8 | （Phase 2）B 在线时 A 发消息 | B 收到 `Event::UnreadChanged = 15`，快照与 `/chat/session/list` 一致 |

## 3. 架构与机制

### 3.1 未读写入：持久化之后、扇出之前，best-effort

```text
DirectMessageService::send
  1. validate / blocklist / can_message
  2. ensure_direct_session            -> session_id
  3. persist_message_and_mailboxes    -> 消息落 Mongo（失败即整体失败）
  4. update_last_message              -> 会话摘要（失败即整体失败）
  5. increment_unread(recipient)      -> 未读 +1（失败只告警，不回滚）   <-- 新增
  6. enqueue_to_device(发送者其他设备 / 接收者设备)
  7. return server_persisted_ack
```

| 选择 | 理由 |
|---|---|
| 放在持久化成功之后 | 未读是派生统计，不能因统计失败让发送失败；顺序错反会出现"未读 +1 但消息没落库" |
| best-effort（`warn!`，不加 `?`） | 与既有"投递尽力而为"一致；漂移由 `POST /chat/session/read` 与前端 `reconcile` 纠正 |
| 单 SQL 原子自增 | `UPDATE … SET unread_count = GREATEST(unread_count + $3, 0) … RETURNING unread_count`，并发安全，不做读改写 |
| 只给收件人加 | 发送者自己的未读不增加；群聊 Phase 1 不计数 |

### 3.2 清零：显式接口 + 幂等

- 入参 `{session_id}`，账号取自 JWT（不信任 body 中的 account_id）。
- SQL 只更新 `(session_id, account_id)` 一行；`UPDATE` 影响 0 行 → 404（会话不存在或不属于该账号），避免越权探测。
- 重复调用天然幂等：已是 0 再置 0，返回 200。
- 与 `DeviceRead` ACK 打通：客户端清未读时上行 `{channel:3, ack_message_id, ack_stage:"device_read"}`，服务端沿用 `shared_handler.rs:164-179` 既有分支，无需新逻辑。

### 3.3 历史拉取：游标 `(created_at, message_id)`

```text
GET /message/history?session_id=<id>&limit=30
GET /message/history?session_id=<id>&limit=30&before_created_at=<rfc3339>&before_message_id=<id>
```

查询条件（命中 `server/src/service/mongodb.rs:338-345` 的复合索引）：

```text
conversation_id = <session_id>
AND (created_at < ?before_created_at
     OR (created_at = ?before_created_at AND message_id < ?before_message_id))
ORDER BY created_at DESC, message_id DESC
LIMIT ?limit
```

- `next_cursor` 取本页最后一条的 `(created_at, message_id)`；不足 `limit` 条返回 `null`，客户端停止翻页。
- 返回 `MessageBody`（与 WS 帧同构），客户端可复用 `ingestMessage` 的去重逻辑。
- 权限：先用 `peer_account_id_in_session`（`ports/message.rs:78-84`）确认调用者在会话内，否则 403。

### 3.4 `ws_url` 下发

```toml
[chat_gateway]
public_ws_url = "ws://127.0.0.1:19967/ws"   # 新增：浏览器可达地址
```

- 缺省回退 `ws://{server.ws.host}:{server.ws.port}/ws`（仅开发方便），生产必须显式配置。
- `/ws/ticket` 一次返回票据 + 地址，浏览器少一次往返。

### 3.5 Phase 2：`Event::UnreadChanged = 15`

计数变化（自增/清零）后，向该账号所有在线设备（`DeviceConnectionRegistry::online_device_ids`，`crates/app_core/src/ports/message.rs:48`）投递快照帧：

```json
{ "status": 2, "event": 15, "channel": 3, "uid": 0, "room_id": "",
  "send_id": "", "sync_id": "", "msg_type": 0, "send_at": "…",
  "payload": {"type": "Unread", "content": {"total": 7, "by_room": [{"room_id": "<id>", "unread": 3}]}} }
```

- 语义是**全量覆盖**，客户端不累加，天然解决多端与跨标签页一致。
- 与 Phase 1 的 `GET /chat/session/list` 不冲突：推送到达即覆盖，丢失由下一次 `reconcile` 兜底。

## 4. 协议与数据结构

### 4.1 `POST /chat/session/read`（新增）

| 项 | 内容 |
|---|---|
| 认证 | `Authorization: Bearer <JWT>`（与既有接口一致，`session_handlers::authenticated_session`） |
| 请求 | `{"session_id": "<uuid>"}` |
| 成功 | `200 {"session_id":"<uuid>","unread_count":0}` |
| 幂等 | 重复调用同样 200 |
| 失败 | `400` session_id 为空/非法；`403` 会话不属于该账号；`404` 会话不存在；`503` 数据库错误 |

### 4.2 `GET /message/history`（新增）

| 参数 | 必填 | 说明 |
|---|---|---|
| `session_id` | 是 | 会话 ID（= `conversation_id`） |
| `limit` | 否 | 默认 30，上限 100（超过截断，不报错） |
| `before_created_at` | 否 | RFC3339（`created_at` 下界游标） |
| `before_message_id` | 否 | 与 `before_created_at` 同时提供才生效 |

响应：

```json
{ "messages": [ /* MessageBody 数组，按 created_at DESC */ ],
  "next_cursor": { "created_at": "2026-10-26T06:20:00Z", "message_id": "<uuid>" } }
```

`next_cursor` 为 `null` 表示已到最早一页（本页条数 < `limit`）。

### 4.3 `POST /ws/ticket`（扩展）

```json
{ "ticket": "<32 字节随机串>", "expires_in_seconds": 30,
  "ws_url": "ws://127.0.0.1:19967/ws" }
```

- 兼容性：只增字段，旧客户端按既有结构解析不受影响。

### 4.4 端口扩展（`DirectChatSessionRepository`）

```rust
async fn increment_unread(
    &self,
    session_id: &str,
    account_id: u64,
    delta: i64,

async fn clear_unread(&self, session_id: &str, account_id: u64) -> Result<(), String>;

// Phase 2：一次取回该账号所有会话未读，用于推送快照
async fn unread_by_session(&self, account_id: u64) -> Result<Vec<(String, i64)>, String>;
```

### 4.5 端口扩展（`MessageStore`，`server/src/chat/port.rs:22-45`）

```rust

    &self,
    conversation_id: &str,
    cursor: Option<(chrono::DateTime<chrono::Utc>, String)>,

```

`UnavailableStore`（`server/src/service/mongodb.rs:194-233`）需补一个返回空 `Vec` 的实现，保持"无 Mongo 时服务可启动"的既有特性。

## 6. 边界、风险与回滚

### 6.1 一致性边界

| 场景 | 处理 |
|---|---|
| 未读自增失败（PG 抖动） | 只 `warn!`，发送照常成功；用户下次进入会话清零，或由前端 `reconcile` 以服务端为准 |
| 消息持久化成功但进程崩溃 | 未读偏少（漏计），不会偏多；清零接口幂等，不影响正确性 |
| 同一消息重投 | `persist_message_and_mailboxes` 按 `message_id` 幂等（`main` 唯一索引，`mongodb.rs:329-337`），但 `increment_unread` 不在同一事务内 → 重投会重复 +1。**约束**：`send` 入口靠 `send_id` 唯一性由客户端保证，服务端不重复调用；如后续引入重试，需把自增移到幂等写入成功分支内（返回"是否新插入"）|
| 并发清零与自增 | 两条 `UPDATE` 无读改写，最终值取决于语句顺序；最坏情况是"清零后立刻 +1"，符合用户预期 |
| 群聊 | 不计数；`unread_count` 保持 0，`/chat/session/list` 对群聊不返回未读 |

### 6.2 兼容性

| 变更 | 兼容性 |
|---|---|
| trait 增方法 | 仓内实现点共 3 处（PG + 2 个 `FakeSessions`），全部同步补齐；不影响外部 crate |
| `/ws/ticket` 加字段 | 只增不改，旧客户端忽略即可 |
| 新增路由 | 不影响既有路由表 |
| `Payload::Unread` | Phase 2 再加，届时 Rust/TS/桌面端同一批次上线 |

### 6.3 回滚

| 粒度 | 操作 |
|---|---|
| 关闭未读写入 | 去掉 `service.rs` 里那一次 `increment_unread` 调用；SQL 与 trait 保留（不影响行为） |
| 关闭清零接口 | 删除路由；客户端 `POST /chat/session/read` 失败后由 `reconcile` 容错 |
| 关闭历史接口 | 删除路由；Web 端回退到 `messages?limit=100` |
| 关闭 `ws_url` | 客户端回退到内置默认地址（需保留一处兜底常量） |

### 6.4 性能

| 点 | 评估 |
|---|---|
| 未读自增 | 1 次按主键 `(session_id, account_id)` 的 UPDATE，走 PK 索引，无需新索引 |
| `GET /chat/session/list` | 已按 `account_id, member_state, session_id` 建索引（`direct_chat_sessions.sql:35-36`），未读列在同表，无额外 JOIN |
| 历史查询 | 命中现成复合索引 `(conversation_id, created_at, message_id)`，`limit ≤ 100` |
| 推送未读快照（Phase 2） | 每次计数变化一次 `unread_by_session`，单账号会话数通常 < 100，可接受；量大时改为防抖 200ms |

### 7.2 手工验证

```powershell
cd d:\rust\live-chat-server
cargo test -p server
cargo run -p server   # 观察启动日志与路由注册
```

1. `POST /ws/ticket`（带 Bearer JWT）→ 响应含 `ws_url`。
2. A 向 B 发消息 → `psql` 查 `im_2024.chat_session_members`，B 行 `unread_count` +1。

6. `GET /message/history` 用不属于该会话的 JWT → 403。

### 7.3 与客户端联调顺序

1. 服务端 P0 先上（`increment_unread` + `/chat/session/read` + `ws_url`）。
2. Web 端 P0 再上（订阅未读 + 覆盖校准 + 全局连接）。
3. 服务端 P1（history）与 Web 端 P2 同批。
4. Phase 2 推送最后上，灰度开关为"客户端忽略 `event=15` 即回退到 REST 校准"。
