# 单聊与群聊实时收发计划

## 1. 目标与范围

- 目标：`/im` 页面的单聊、群聊可以通过长连接（WS）实时收发，并通过 REST 完成历史同步。
- 范围内：单聊（`MsgChannel::single`）、群聊（`MsgChannel::group`）、会话列表、ACK。
- 范围外：公共频道（`MsgChannel::public`，直播间）。公共频道保持现状，本计划不修改其行为。
- 约束：
  - 主后端 `8080` 属于其他服务，本计划不修改其配置、路由和逻辑。
  - 聊天长连接使用独立端口与独立配置段，不复用 `application.toml` 中 `[im.ws]` 指向的既有地址。
  - JWT 由主后端签发，聊天服务只验签，不签发。
  - 不新增 `chat_id` 作为会话标识，统一使用 `conversation_id`（单聊=`session_id`，群聊=`group_id`）。

## 2. 已确认的现状（依据代码）

| 项 | 现状 |
|---|---|
| 服务端 WS | `server/src/app.rs` 中 `/ws` 在 `server.ws.port`（19967）。握手可匿名连接；仅带 `Authorization` 头时绑定身份。 |
| 浏览器 WS 认证 | 浏览器 WebSocket 无法设置 `Authorization` 头，客户端当前只能匿名连接，无法发送单聊、群聊。 |
| JWT | 主后端签发，写入 HttpOnly Cookie `v2_access_token`。聊天服务用 `COLA_JWT_SECRET` 以 HS256 验签。 |
| 单聊发送 | `/message/send` 要求 `recipient_uid`，`DirectMessageService::send` 完成校验、会话创建、持久化和投递。 |
| 群聊发送 | `GroupMessageService::send` 以 `group` 参数（当前取自 `message.room_id`）作为群 ID，校验 `group_memberships` 成员关系。 |
| 群 ID 字段 | `MessageBody.room_id` 同时承担公共房间和群 ID，语义混淆。 |
| 群数据 | PG `im_2024.group_memberships(group_id TEXT, account_id BIGINT, status)` 已有表。缺少建群、加人接口。 |
| 客户端 `/im` | 只有 HTTP 收发（`/api/im/messages`、`/api/im/sessions`），没有 WS；单聊发送缺 `recipient_uid`；`setInterval` 注入假回复。 |
| 客户端 Cookie | `v2_access_token` 为 HttpOnly，脚本不可读取，只能由同源服务端代理读取。 |

## 3. 架构方案

### 3.1 新增长连接服务配置（独立段）

在 `application.toml` 新增独立段（不修改 `[server.ws]` 与 `[im.*]` 既有字段）：

```toml
[chat_gateway]
host = "0.0.0.0"
port = 19968                 # 聊天长连接专用端口，与现有 19967 区分
ticket_ttl_seconds = 30
max_message_bytes = 65536
```

- 服务端新增 `chat_gateway` 配置模型，启动时校验端口、TTL、最大消息大小的合法范围，并提供安全默认值。
- 为避免与现有 `/ws` 冲突，新长连接服务挂载在独立端口上。
- 注：`server/src/config.rs` 已有 `[server.ws]`，本次新增的 `[chat_gateway]` 与之并存，不修改其含义。

### 3.2 WS 认证：一次性票据（ticket）

```text
浏览器 /im                 客户端同源代理                 聊天服务
   |  POST /api/im/ws-ticket     |                              |
   |---------------------------->| 读取 HttpOnly v2_access_token |
   |                             | POST /ws/ticket (Bearer JWT) |
   |                             |----------------------------->| 验签 JWT，签发 ticket(30s,一次性)
   |                             |<-----------------------------| {ticket, expires_at}
   |<----------------------------| {ticket}                     |
   |  new WebSocket(ws://.../ws?ticket=...)                     |
   |------------------------------------------------------------>| 消费 ticket（原子删除），绑定身份
```

- ticket 为 32 字节随机值（`rand`/`uuid` v4 不足时使用安全随机源），仅存服务端内存（`DashMap` 或 `Mutex<HashMap>`），带过期时间，握手时原子消费。
- JWT 不出现在 URL 中，不进入浏览器脚本；ticket 只能使用一次，过期即失效。
- 握手日志只记录 ticket 的前 6 位摘要，不记录完整值。
- 后续保留 `Authorization` 头的握手方式（已有逻辑），便于非浏览器客户端。

### 3.3 客户端同源代理

- 新增 `src/routes/api/im/ws-ticket/+server.ts`：校验登录、读取 `v2_access_token`、调用聊天服务 `POST /ws/ticket`，返回 `{code, message, data: {ticket, expires_at}}`。
- 聊天服务地址读取 `application.toml` 的 `[im.gateway]`（已存在，指向 `127.0.0.1:19967` 的 HTTP 接口）的同级配置，不新增读取 `8080` 的逻辑。
- 错误不泄漏内部细节，日志脱敏（沿用 `redactImLogValue`）。

### 3.4 消息模型

- 服务端 `MessageBody` 与客户端 `MessageBody` 同时新增可选字段 `conversation_id`（`Option<String>`，`skip_serializing_if`）。
- 语义：
  - 单聊：`conversation_id` = 会话 `session_id`（UUID 字符串），由服务端在 `ensure_direct_session` 后回填；客户端发送时可只带 `recipient_uid`。
  - 群聊：`conversation_id` = `group_id`（TEXT），由客户端发送，服务端校验成员关系。
- `room_id` 保留给公共频道，群聊不再使用 `room_id` 承载群 ID。
- 服务端 `dispatch_authenticated` 群聊分支改读 `conversation_id`；兼容期内若 `conversation_id` 为空则回退读 `room_id`，并记录告警（兼容完成后移除回退）。

### 3.5 群聊数据接口

- 新增最小接口（仅群聊必需）：
  - `POST /group/create`：创建群，写入 `group_memberships`（创建者为成员）。
  - `POST /group/members/add`：群主或成员加人（本阶段仅校验调用者为成员）。
  - `GET /group/list`：返回当前账号所属群列表（`status = 1`）。
- 这些接口只在聊天服务中实现，主后端不改动。
- `group_id` 使用服务端生成的 UUID 字符串，避免客户端伪造。

### 3.6 客户端 `/im`

- 页面挂载时：`POST /api/im/ws-ticket` 获取票据，建立 `ws://<chat_gateway>/ws?ticket=...`。
- 收到服务端推送的 `MessageBody`：按 `channel` 与 `conversation_id` 归入对应会话，单聊与群聊都更新列表与未读数。
- 断线：指数退避重连（上限 30 秒），重连前重新获取 ticket（ticket 为一次性）。
- 发送：单聊 `channel=single` + `recipient_uid`；群聊 `channel=group` + `conversation_id`。发送失败标记为 `failed`，不再显示为成功。
- 移除 5 秒假回复定时器（`replyTimer`），移除 `createLocalSessionFromQuery` 的本地假会话分支（后端不可用时仅提示）。
- 保留现有 REST 同步作为历史拉取。

## 4. 分阶段实施与验收

### 阶段 A：服务端配置与独立长连接服务

- 新增 `chat_gateway` 配置段与校验（端口、TTL、消息大小）。
- 启动独立 WS 服务（端口 `chat_gateway.port`），仅提供 `/ws`。
- 验收：`cargo check --workspace` 通过；配置单元测试覆盖默认值与非法值。

### 阶段 B：ticket 认证

- 实现 `POST /ws/ticket`（需要 Bearer JWT，验签沿用 `session_handlers::authenticated_session` 的逻辑，不修改其行为）。
- 实现 ticket 存储、过期、一次性消费。
- 握手：`?ticket=` 有效则绑定身份，无效则拒绝握手（HTTP 401）。
- 验收：单元测试覆盖签发、重复消费、过期、伪造；集成测试用 `curl`/`ClientWebSocket` 验证握手。

### 阶段 C：消息模型与单聊

- 两端 `MessageBody` 新增 `conversation_id`。
- 单聊：`recipient_uid` 必填；服务端回填 `conversation_id = session_id`；投递到接收方所有在线设备。
- 落库不依赖副本集：`[mongodb].transactions = "auto"` 时，standalone 单机自动降级为顺序幂等写入（`messages`/`outbox`/`inbox` 各自幂等 upsert），详见架构计划 5. MongoDB「落库模式」。
- 验收：单聊两个账号互发，接收方 WS 实时收到；离线消息通过 `/message/sync` 拉取。

### 阶段 D：群聊

- 新增群接口（3.5）。
- 群聊发送改用 `conversation_id`；服务端校验成员、投递给所有在线成员设备（排除发送设备）。
- 验收：三成员群，发送方外的两人实时收到；非成员发送被拒绝（`forbidden`）。

### 阶段 E：客户端 `/im`

- 3.6 中的改动。
- 验收：`npm run check` 通过；页面可建立 WS 并收到推送；断线后自动重连。

### 阶段 F：整体验证

- 服务端 `cargo test --workspace`（沿用现有失败用例需单独说明，不计入本次）。
- 端到端：两个账号单聊、群聊实时收发，断线重连，ticket 过期。

## 5. 风险与待确认

1. **ticket 存储在单进程内存中**：多实例部署时需改为 Redis 等共享存储。当前部署为单进程，记录为限制。
2. **`/message/sync` 对群消息的覆盖**：当前 `pending_for_device` 只按收件人读取，群消息需确认收件人写入逻辑（见 `persist_message_and_mailboxes` 的 `recipient_account_ids`）。
3. **`conversation_id` 兼容期**：旧客户端仍用 `room_id` 发群消息的回退期限需确定，本计划暂定"一个版本"。
4. **JWT 与设备**：JWT 中的 `device_id` 由主后端签发，ticket 绑定该设备；同一账号多设备并存已由 `ChatHub` 支持。
5. **测试限制**：PG、MongoDB 为外部服务，集成测试依赖其可用性；无法在本环境全部验证时，需在结果中说明。当前线上 MongoDB 为 standalone 单机，消息落库按 `[mongodb].transactions = "auto"` 自动降级为顺序幂等写入，不再出现多文档事务 `code 20`；若后续改为单节点副本集，`auto` 会自动回到事务路径，无需改代码。
6. **现有失败用例**：`config::tests::parses_current_application_config` 断言的 `chat_mongo` 与当前配置 `cola_im_2024` 不一致，属于既有问题，本计划不修复，但新增配置段时会一并保证该测试的数据不变。

## 6. 待确认事项

- 聊天长连接端口 `19968` 是否可用、是否需要对外开放防火墙。
- 群接口是否需要群主权限模型（本计划暂定任一成员可加人）。
